# Cobertura de Telas e Mapeamento de Fórmulas — Dashboard

Este documento mapeia todas as telas, rotas, endpoints e fontes de dados da aplicação front-end (`moneta-dashboard`), categorizando a situação de cada uma:
- **(a)** Alimentada por tabela existente → o seed preenche diretamente.
- **(b)** Calculada a partir de transações, contas ou categorias → os dados são calibrados para gerar resultados realistas.
- **(c)** Dados fixos no código ou sem endpoint → não preenchida por banco; catalogada como lacuna.

## Síntese de Cobertura

- **Telas alimentadas por tabelas existentes (a)**: Lançamentos (`deals`), Notificações (header), Preferências de Notificação (`settings`).
- **Telas com lógica calculada pelo backend sobre dados do banco (b)**: Visão Geral (`overview`), Categorias (`pipeline`), Contas (`customers`), Orçamentos (`team`), Previsões & Riscos (`forecasting`), Relatórios (`reports`), Busca Global (`search`).
- **Lacunas de interface (c)**:
  1. *Aba Perfil de Ajustes*: `settings.tsx` possui campos estáticos no JSX ("Felipe Administrador", "admin@moneta.com.br") em vez de consumir `useUserProfile()`. No entanto, o **Header** e o **Avatar** consomem `useUserProfile()` dinamicamente e exibem o nome real da empresa e as iniciais corretas.
  2. *Gráfico de Fluxo de Caixa*: a visualização do gráfico de área em `revenue-chart.tsx` contém meses Jan–Set e Nov–Dez com pontos de dados estáticos para demonstração estética de série anual, consumindo o dado dinâmico real da API para o mês consolidado de Outubro.
  3. *Aba Integrações & Segurança*: informativo estático sobre a stack do sistema.
  4. *Fórmula Discreta de Regularidade de Contas*: O cálculo de `regularityPct` no backend (`AccountService.java`) utiliza faixas fixas baseadas exclusivamente nos dias desde o último lançamento (`days < 10` $\rightarrow$ 98%, `10..29` $\rightarrow$ 88%, `30..59` $\rightarrow$ 75%, $\ge 60$ $\rightarrow$ 60%), possuindo apenas 4 patamares discretos sem variação contínua. Para evitar concentração excessiva, o seed distribuiu ativamente a inatividade das 16 contas entre as 4 faixas (6 contas em 98%, 5 em 88%, 3 em 75% e 2 em 60%), garantindo que apenas 37,5% das contas fiquem na faixa superior (cumprindo a regra de no máximo 50%).
